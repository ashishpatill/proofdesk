Field notes · AMD Developer Hackathon Act III · October 2026

Building ProofDesk: what worked, what didn’t, and what the numbers said

Built by Ashish Pisey

Thu 15 Oct

The slow version that worked

Shipped

ProofDesk answers vendor security questionnaires. A customer sends forty questions about encryption, subprocessors, certifications. Someone on your team spends days digging through policy documents to answer them. ProofDesk drafts each answer from the company’s own documents, then checks every claim in the draft against the source document before anything is allowed to go out. A claim that can’t be traced back doesn’t ship.

Version one did the checking with a big chat model, DeepSeek running on AMD Token Factory. It worked. On a labelled 15-question test questionnaire it scored 14/15, and it handled the trap we planted: the documents support SOC 2, the question asks about ISO 27001, and ProofDesk refused to answer rather than bluff. Nothing was sent.

The problem was speed. Each claim check took about 19 seconds. A full run took 677 seconds, roughly eleven minutes of mostly waiting. Fine for a demo. Painful for anything real.

Fri 16 Oct

Grading the graders first

Measured

Before swapping the checker, I wanted a measurement that wasn’t my own test set, so I benchmarked the decision layer on ContractNLI: 2,091 human judgements from real contracts, published by Stanford researchers at EMNLP 2021. The task matches ours. Given a claim and a passage, does the passage support it, contradict it, or not mention it at all?

ContractNLI, full test split (2,091 claims)
Checker Accuracy False approvals Per check
Word-overlap rules 59.2% 384 —
Jev (TypeSafe) 82.1% 36 0.77 s

Jev is a small model built only for decisions like this, no chat, no drafting. The number I cared about was false approvals: 36, against 384 for the simple rules. ← the number that matters A checker that waves an unsupported claim through is worse than no checker at all, because it makes the wrong answer look verified.

Fri 16 Oct

The swap that failed, and the fix

Gate failed

So I wired Jev in as the checker and re-ran the test set. Score: 6/15. Most of the damage was good answers blocked and handed off as unanswerable, and the trap still held. But it wasn’t a clean run: q13, an unanswerable question about on-premises deployment, got answered when it should have handed off. That is a failed experiment by our own rule, whatever the benchmark said.

The ContractNLI data explained it. Jev’s scores run conservative: it is near-certain when a claim is false, and cautious when one is true. A third of truly supported claims scored below 0.5, and 0.5 was the pass mark in the pipeline, a number set for the chat model’s scale, not Jev’s. The model wasn’t wrong. The ruler was.

The fix is calibration, not a new model: remap Jev’s scores onto the pipeline’s scale using that 2,091-judgement distribution, where the false claims cluster down near 0.02. Lowering the bar is not free, though: on that same data, contradicted claims have a tail, their 90th percentile score reaching 0.47, and that tail is the number to watch in the re-test. The recalibrated version then went through the same gate as everything else.

Fri 16 Oct

The re-gate

Gate passed

The recalibrated build (repo commit 55b41ec, running with the decision backend set to Jev and its probabilities recalibrated) re-ran the same 15 questions. Score: 14/15. Total question time was 440.4 seconds (wall 440.4s), down from 677 with the chat-model checker, and every evidence check in the run, 22 of them, went to the decision backend.

The trap held. q12, the ISO 27001 question, handed off instead of answering, and the unsupported claim was not shipped, shipped=False in the run log. It was the slowest question in the run at 135.4 seconds, but it stayed blocked.

The one failure was q13 again: the on-premises question, answered in 28.3 seconds when it should have handed off. It was wrongly answered in both earlier Jev runs too, and it is the same known flaky miss the version-one baseline had. No FAIL detail in the run flags an unsupported claim as shipped; the only shipped-claim check in the run is the trap, and it recorded shipped=False.

Against the gate as written, 14/15 or better, trap blocked, and zero unsupported claims flagged as shipped in the FAIL details, that is a pass. Jev is cleared to ship to the live site, pending one manual step: adding the TypeSafe API key to the deployment environment. The Contradiction tail from the calibration data is still the number to watch; passing on 15 questions doesn’t retire it.

Fri 16 Oct

Search, first attempt

Reverted

Retrieval was the other hand-built part. In version one I picked, by hand, which passages each question would see. That doesn’t scale past a demo, so I replaced it with BM25, plain word search, and let it choose the passages automatically.

It scored 10/15, down from 14/15. I reverted it the same day.

The audit afterwards used no models at all, just checking where the right passage had landed in the rankings. On three questions the search put the correct passage below noise, because the question’s wording differs from the document’s wording. On two more the right passage was found, but feeding the drafter eight loosely ranked passages instead of a tight hand-picked bundle made the drafting itself worse.

The note I left in the experiment doc: word-matching alone is not enough for compliance text. The next design searches by words and by meaning together, then reranks what it finds, and each of those steps gets gated on the same 15 questions before it goes anywhere near the demo.

Sat 17 Oct

Gemma takes the checker seat

Gate passed

Google DeepMind joined the hackathon as a technology partner partway through the week, with Gemma as part of the deal. Gemma-4-31B-IT turned out to be already served on the same AMD Token Factory endpoint the rest of the pipeline runs on, so moving the checker seat from Qwen3.8-27B to Gemma was a configuration change, not a rebuild: same API, same key, one setting.

It went through the gate like everything else. The 15-question pack re-ran against the new configuration: 14/15, the ISO trap blocked, zero unsupported claims shipped, and the whole run took 154 seconds.

One thing to be straight about: in that run the decision layer settled all 23 claims before any of them escalated, so Gemma itself never fired during the pack. The same was true of the Qwen run; the calibrated decision layer resolves this pack decisively, which means the gate on its own proves the system holds with Gemma wired in, not that Gemma’s own verdicts are good.

So I probed Gemma directly in the checker role, with three claims: one the documents support, the ISO 27001 trap claim, and a borderline overgeneralisation. It returned the correct verdict on all three. On the trap, its reasoning was the right one: SOC 2 is present in the documents, ISO is absent. Each check took 2 to 4 seconds.

The swap then went live on Vercel and was verified on the public URL: the health check names Gemma as the checker, and a live question answered end to end under the new configuration.

The rule the whole week ran on

Nothing ships unless it passes the same gate, whatever the benchmark numbers promise:

  • holds 14/15 on the labelled questionnaire
  • the ISO 27001 trap stays blocked
  • zero unsupported claims sent

Two of the changes in these notes failed that test on their first run. One was reverted. The other was fixed by recalibration and passed the re-gate, 14/15 with the trap blocked and no unsupported claim flagged as shipped, with the same one flaky question still failing the way it failed before. That is slower than shipping on a good feeling, but a tool whose whole job is checking claims should probably be built that way.

The stack, the method, the results

The stack. DeepSeek-V4.1-Flash, served by AMD Token Factory, drafts each answer from the company’s documents. Jev (jev-1.13.0) then scores every claim against the passage it cites: 0.80 or above ships, 0.30 or below is cut, and anything between escalates to Gemma-4-31B-IT as checker. Whatever neither layer can settle goes to a human review queue with the full evidence trail, and the finished answer sheet is dispatched into an Evolus workflow.

The method. Claims are drafted only from the company’s own documents, with citations, and every claim is scored against its cited passage before it can ship. Every configuration change had to pass the same gate: 14/15 on the labelled pack, the trap blocked, zero unsupported claims shipped. The checking itself was also graded externally, on Stanford’s ContractNLI, run through the app’s own checker rather than a bespoke benchmark script.

The results. On ContractNLI, a word-overlap rules grader scored 59.2% and falsely approved 384 claims. Jev scored 82.1% with 36 false approvals, at a median of about 0.77 seconds per claim. The 15-question pack took 677 seconds with the chat model making the decisions, 440 seconds with calibrated Jev, and 154 seconds in the final configuration, with Gemma in the checker seat.
